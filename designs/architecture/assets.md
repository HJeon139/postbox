# Attachments and assets

Part of [the architecture](../architecture.md).

**Attachments.** Files are stored by the SHA-256 of their contents under `blobs/ab/cdef…`, so identical files are kept once and corruption is detectable. The log holds only metadata: `{ id, name, type, size, sha256 }`. Files are served with `X-Content-Type-Options: nosniff` and a `sandbox` content-security policy. Only PNG, JPEG, GIF and WebP images are shown inline; everything else downloads. Large content never enters the log, so snapshots stay small. An agent reads an attachment from its path on disk: the turn a message is sent to gets the paths in that message, and every other agent in the room gets them in its history, catch-up, a topic thread’s opener and the read tools (#671). An agent on a remote host has only the turn’s own copies, so it gets the names, and a line saying its host can’t open them yet.

**Assets** (#516, its slice S3, whose decisions the person settled on 2 November 2026). Files agents publish to their conversation keep their bytes the same way, in a folder of their own, `assets/ab/cdef…`, so the only files deleted are ones nothing else stores. The state key `assets` holds each asset’s versions, metadata only: name, size, type, hash, author, time and base, with a hash of `null` for a delete. Every write goes through one function commit (`server/assets.mjs`), which on the applied state checks the base, the name (unique in the room, ignoring case), the bounds (`ASSETS` in `shared/limits.mjs`) and the room’s budget, and writes the version and what it prunes as one fsynced line. So a version exists only once the disk has it, of two writes from one base exactly one wins, and a repeat, by its `op` and author or by the head’s base, bytes and author, makes no second version. Each check is a lookup, not a scan: the reducer keeps each room’s index in `assetRooms` (its assets, its live names, the files its kept versions hold with how many hold each, their bytes and its ops), so a write costs the same however many assets Postbox holds, and version v is always the asset’s `versions[v - 1]`. Text keeps every version, and a large binary its last few (`server/asset-retention.mjs`). Each commit prunes only the version it makes prunable, so lowering `largeBinaryBytes` or `binaryVersionsKept` later prunes nothing already past the new window: it applies to versions written from then on. A prune or an erased conversation puts its hashes in `assetReleases`, and only the load deletes their files, before any write can start, and only those no version in any room keeps (`server/asset-orphans.mjs`). A file nothing names and nothing released, from a write that never committed or from metadata an older Postbox dropped, is kept and counted in the log, never deleted. The three keys and the four asset events are public: they carry metadata, never an asset’s contents, as `files` does. Agents reach assets through seven tools (`server/asset-tools.mjs`): `list_assets`, `read_asset`, which reads a text version in parts that its first part pins to one version, `search_assets`, and `write_asset`, `rename_asset`, `delete_asset` and `restore_asset`, each naming the base version it read. An agent on a remote host gets them through Postbox, with text only, since a path there names a file Postbox can’t read.

**Searching assets** (#516, 10 November 2026; `server/asset-search.mjs`). Assets took the place of the corpus, a separate store of bundled books and the datasets agents loaded with `add_dataset`: data an agent brings in is a room asset. Search reads each live text asset’s newest version from its blob, splits it into passages of about 60 to 180 words, and indexes them with BM25 (`shared/bm25.mjs`), with the stub’s meaning score beside it. A room’s index is built the first time it’s searched and kept while its assets’ heads stay the same (the key is each indexed asset’s id, version, hash and name, so a rename rebuilds it), for the eight rooms searched most recently. A hit names its asset, the version it was read from, and the passage. One function answers the agent’s `search_assets`, here and on a host (its route is `ask`, as the other asset tools’ are), and an app’s `assets.search` and `assets.list` through the bridge (`server/host-tool.mjs`). Every agent holds its room’s assets, so an app needs only to name those two in its `permissions`; its agent needs no tool for them. An app reads the room of the conversation it was shown in. Apps keep their own data files and `codePath`: those carry an app’s version with it, and an agent on a host already sends them through its broker, which assets don’t replace.
