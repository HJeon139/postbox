# Attachments and assets

Part of [the architecture](../architecture.md). Files people attach and files agents publish to their conversation, kept by their contents beside the event log ([store.md](store.md)).

## Attachments

Files are stored by the SHA-256 of their contents under `blobs/ab/cdef…`, so identical files are kept once and corruption is detectable. An upload (`POST /api/files`, `server/upload.mjs`) has no fixed size limit: it streams into the store (`Blobs.putStream`), hashed as it’s written to a draft that is synced and renamed under its hash, so memory stays at a chunk whatever the size. An upload that would leave less than 1 GB free on the disk is refused (507) with that reason, before it’s written when the browser sends its size, and as soon as the disk fills while it streams in; a refusal removes the draft, and the rest of the body is read and dropped, so the page gets the answer (#870). A draft a killed or crashed Postbox left, at the store’s root or beside a blob, is removed at start, under the data folder’s lock, once its process is no longer running (`server/blob-drafts.mjs`). The log holds only metadata: `{ id, name, type, size, sha256 }`. Files are served streamed, a chunk at a time, and checked against their hash as they go, so a damaged file is cut off before its end (`Blobs.stream`), with `X-Content-Type-Options: nosniff` and a `sandbox` content-security policy. Only PNG, JPEG, GIF and WebP images are shown inline; everything else downloads. Large content never enters the log, so snapshots stay small. An agent reads an attachment from its path on disk: the turn a message is sent to gets the paths in that message, and every other agent in the room gets them in its history, catch-up, a topic thread’s opener and the read tools (#671). An agent on a remote host has only the turn’s own copies, so it gets the names, and a line saying its host can’t open them yet.

## Assets

From #516’s slice S3. Files agents publish to their conversation keep their bytes the same way, in a folder of their own, `assets/ab/cdef…`, so the only files deleted are ones nothing else stores. The state key `assets` holds each asset’s versions, metadata only: name, size, type, hash, author, time and base, with a hash of `null` for a delete. Every write goes through one function commit (`server/assets.mjs`), which on the applied state checks the base, the name (unique in the room, ignoring case), the bounds (`ASSETS` in `shared/limits.mjs`) and the room’s budget, and writes the version and what it prunes as one fsynced line. So a version exists only once the disk has it, of two writes from one base exactly one wins, and a repeat, by its `op` and author or by the head’s base, bytes and author, makes no second version. Each check is a lookup, not a scan: the reducer keeps each room’s index in `assetRooms` (its assets, its live names, the files its kept versions hold with how many hold each, their bytes and its ops), so a write costs the same however many assets Postbox holds, and version v is always the asset’s `versions[v - 1]`. Text keeps every version, and a large binary its last few (`server/asset-retention.mjs`). Each commit prunes only the version it makes prunable, so lowering `largeBinaryBytes` or `binaryVersionsKept` later prunes nothing already past the new window: it applies to versions written from then on. A prune or an erased conversation puts its hashes in `assetReleases`, and only the load deletes their files, before any write can start, and only those no version in any room keeps (`server/asset-orphans.mjs`). That rests on two counts, the rooms’ indexes and, once per load, a recount of the unpruned versions themselves: where they disagree, the file stays, still released, and the log names its hash and room, since a delete can’t be undone (#691). A write the commit refuses (a stale base, a taken name, the budget) removes the file it made, unless another write of the same bytes holds or kept it; a file that was there before the write is never removed (#706), so an agent retrying it doesn’t grow the disk. A file nothing names and nothing released, from a write cut off before its commit or from metadata an older Postbox dropped, is kept and counted in the log, never deleted. A write’s draft, from a Postbox killed before the rename, isn’t such a file: it’s removed at start once its process is no longer running, as the attachments’ drafts are (`server/blob-drafts.mjs`). The three keys and the four asset events are public: they carry metadata, never an asset’s contents, as `files` does. Agents reach assets through seven tools (`server/asset-tools.mjs`): `list_assets`, `read_asset`, which reads a text version in parts that its first part pins to one version, `search_assets`, and `write_asset`, `rename_asset`, `delete_asset` and `restore_asset`, each naming the base version it read. An agent on a remote host gets them through Postbox, with text only, since a path there names a file Postbox can’t read.

## Viewing assets and changed files

From #1446. The person reads an asset, or a file the agents changed, in Work’s viewer. Two GET routes serve it, each only for the conversation in its path (`server/room-files.mjs`): `/api/threads/:id/assets/:assetId?v=` an asset’s version, the newest by default, and `/api/threads/:id/work/files/:fileId/content` a changed file from the copy the work ledger kept after the agents’ last change, never the file on disk now. An asset of another room, a deleted asset at any of its versions, a pruned version and a missing blob are the same 404. Both send `/api/files`’s headers, with `nosniff`, a `sandbox` content-security policy and `Cross-Origin-Resource-Policy: same-origin`. PNG, JPEG, GIF and WebP come inline as themselves. Any other text, HTML and SVG included, comes inline as `text/plain`, at most its first `VIEWER.textBytes` (`shared/limits.mjs`), cut at a character’s edge, so it reads as source and never runs. Bytes that aren’t text come as a download, and `?download=1` downloads anything, whole.

## Searching assets

From #516 (`server/asset-search.mjs`). Data an agent brings in is a room asset: there’s no separate corpus or dataset store. Search reads each live text asset’s newest version from its blob, splits it into passages of about 60 to 180 words, and indexes them with BM25 (`shared/bm25.mjs`), with the stub’s meaning score beside it. A room’s index is built the first time it’s searched and kept while its assets’ heads stay the same (the key is each indexed asset’s id, version, hash and name, so a rename rebuilds it), for the eight rooms searched most recently. A hit names its asset, the version it was read from, and the passage. One function answers the agent’s `search_assets`, here and on a host (its route is `ask`, as the other asset tools’ are), and an app’s `assets.search` and `assets.list` through the bridge (`server/host-tool.mjs`). Every agent holds its room’s assets, so an app needs only to name those two in its `permissions`; its agent needs no tool for them. An app reads the room of the conversation it was shown in. Apps keep their own data files and `codePath`: those carry an app’s version with it, and an agent on a host already sends them through its broker, which assets don’t replace.
