# Diagram legibility: estimate, then measure

Part of [the architecture](../architecture.md).

**Decision.** Two checks find Mermaid diagrams too small to read, and a third, on the server, finds one Mermaid can’t parse (“Syntax, checked on the server”, below). All three reach the agent as a `lint` message that says what to change. Each diagram is reported once.
- **The estimate** ([`shared/diagram-lint.mjs`](../../shared/diagram-lint.mjs)) runs on each finished reply. It reads the Mermaid source well enough to estimate the layout’s width, and from that the size its text ends up at in the 728 px column. It also flags too many boxes, one row of many boxes, and long sequences.
- **The measurement** happens in the browser after a diagram renders: its text size is 13 px × the scale it was drawn at. Anything under 10 px at the conversation’s width is reported to the server, unless the estimate already caught it.

**What it rests on**
- **It’s the symptom people see.** A wide diagram doesn’t fail; it shrinks. Text size is the measure that matches what a reader experiences, so both checks use it.
- **Fitted, not guessed.** The estimate’s layout constants (8.5 px per character, about 56 px of padding per box, the gaps between sequence participants) were fitted to diagrams rendered in Chrome. They agree to within about half a pixel, and the measured values are a test.
- **Prevention first, by drawing instead.** The agent guide steers a picture that explains away from Mermaid: it asks agents to draw what things are or do in an app, not labeled boxes, and keeps Mermaid for a quick sketch. The maintainer’s blind verdicts on 20 agent-made visuals failed every diagram of labeled boxes, a well-made Mermaid flowchart included ([#206](https://github.com/HJeon139/postbox/issues/206)). The guide used to ask for about five boxes side by side and top-to-bottom chains; for the Mermaid diagrams agents still write, these two checks now carry that advice, in the lint message that says what to change.
- **No loops.** A reply to a lint message isn’t linted again by either check.
- **One pipeline for every check.** Each check returns problems, `{ code, message, scope }` ([`server/checks.mjs`](../../server/checks.mjs)). The runtime gathers the problems one agent turn caused into one lint turn: the server’s checks run when the turn ends, and what the browser reports (a diagram measured or failing to draw, the app check’s warnings) joins them within a moment of rendering. A turn gets at most one lint turn, and a lint turn that only calls tools, such as `define_term`, shows as a one-line note rather than a reply.
- **A reply that should have been a block** ([#63](https://github.com/HJeon139/postbox/issues/63)). Agents drift back to prose over a long session, so every reply is checked for how it ends: options in a list with a question or “pick one”, three or more questions, a draft of 40 lines or more that asks for sign-off, or a Markdown table of ten rows or more. A turn that showed the matching block, or followed a request for Markdown or prose, isn’t flagged. Nor is a reply to another agent, one that @-mentions an agent or goes back to the agents that woke it ([#1695](https://github.com/HJeon139/postbox/issues/1695)): its options, questions and drafts are that agent’s to answer, and a block would land them on the person. Each finding costs a lint turn, so the check is conservative; its lint turn asks for the block and needs no reply.

**Revisit when** another diagram type becomes common (class, state and ER diagrams only get the count check), or Postbox’s column width or diagram font size changes; then re-measure and refit.

## Syntax, checked on the server

**Decision.** A diagram Mermaid can’t parse is found on the server when the turn ends, so its agent hears Mermaid’s message in that turn’s lint turn whether or not the person ever scrolls to it ([#731](https://github.com/HJeon139/postbox/issues/731)). Since diagram frames load only as they near the view ([#701](https://github.com/HJeon139/postbox/issues/701)), the page’s report of a failed diagram waited for the person to scroll there, often after the agent’s turn had ended.
- **Mermaid’s own parser, the one the page uses.** [`server/diagram-parse-worker.mjs`](../../server/diagram-parse-worker.mjs) loads the bundled `app/kit/vendor/mermaid/mermaid.min.js` and the sandbox page’s own script, [`app/kit/diagram.js`](../../app/kit/diagram.js), into a context with a stand-in page, and calls `mermaid.parse` on each diagram as the page would draw it. No new dependency: it is the file the sandbox already loads.
- **In a worker thread, with a time limit.** [`server/diagram-parse.mjs`](../../server/diagram-parse.mjs) keeps one worker for the process, started by the first diagram, and sends diagrams to it one at a time. A diagram that takes longer than 5 seconds ends the worker and gets no answer; the diagrams queued behind it go to a new one. Nothing new is parsed once Postbox is closing. So a diagram that hangs the parser can’t stall Postbox, and the worker’s heap is capped at 256 MB.
- **Only what Mermaid refuses.** Parsing needs no layout, but Mermaid starts DOMPurify, which needs a document; the stand-in gives it one, and DOMPurify’s fast path passes text with no markup. A label with HTML in it, such as `<br>`, fails in the stand-in for that reason, not for its syntax, so it’s left to the page. Only a parse error (Mermaid’s “Parse error”, “Lexical error”, “Parsing failed”, or no diagram type found) is reported.
- **Once per diagram.** While the parser runs, it holds the turn’s lint turn, as an app still being checked does, up to the lint turn’s longest wait of 12 s, so an error joins what the estimate found about the same diagram. The diagram is then remembered on the session, so the page’s report of it later goes nowhere. A source that appears twice in a reply is checked once, and a diagram reported in an earlier turn isn’t checked again.
- **The diagrams the page draws.** The server takes a reply’s diagrams from the renderer’s own output ([`shared/mermaid-blocks.mjs`](../../shared/mermaid-blocks.mjs), from `renderMarkdown` in [`shared/markdown.mjs`](../../shared/markdown.mjs)), each with the text the page reads from its figure. So ``` and ~~~ fences, in a quote or a list item, are diagrams, and a `mermaid-example` fence or one inside math isn’t, exactly as the page draws them.

**What it rests on.** Measured on a Mac with the bundled Mermaid, in Node with the stand-in page: it loads in about 40 ms, parses one diagram in 1 to 17 ms, and the process’s resident memory grows by about 70 MB. It refused an arrow with no target in a flowchart, a dangling label in a class diagram, a bad pie value and an unfinished architecture diagram with Mermaid’s own messages, and passed a flowchart, sequence, class, state, ER, pie, Gantt and mind map diagram ([the probe on #731](https://github.com/HJeon139/postbox/issues/731#issuecomment-7082748330)). The person chose the worker over the main thread and over not parsing on the server.

**Revisit when** Mermaid is updated (rerun the probe: the stand-in page covers what this version’s parse touches), or a diagram type starts needing layout to parse.
