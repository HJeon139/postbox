# Sandboxed pages that load nothing

Part of [the architecture](../architecture.md).

**Decision.** An agent app or diagram page is sandboxed by its response header, `Content-Security-Policy: sandbox allow-scripts allow-forms; …`, not by the iframe’s `sandbox` attribute. It is self-contained:
- **Inline:** the kit, the stylesheet and the diagram script are inlined into the page when it’s served. Before serving an app version for the first time, the server asks V8 to parse each classic inline script and caches any syntax errors with their source positions (#328). It never runs the script; only the sandboxed page does.
- **Libraries:** D3, KaTeX and Mermaid reach it as text over the postMessage bridge, and run as inline scripts. KaTeX’s fonts travel inside its stylesheet as `data:` URLs.
- **Policy:** it allows inline code, `data:` images and fonts, `blob:` audio and images from Postbox’s own `/media/`, and nothing else that loads from a URL. `/media/` sends no `Cross-Origin-Resource-Policy`, because these pages’ origin is opaque and `same-origin` or `same-site` would block every app image; what that leaves another site to learn is written beside `SAME_ORIGIN_ONLY` in [`server/review-files.mjs`](../../server/review-files.mjs) ([#992](https://github.com/HJeon139/postbox/issues/992)). No file Postbox serves allows a cross-origin read (`access-control-allow-origin`, [#1272](https://github.com/HJeon139/postbox/issues/1272)), so these pages load `/media/` only as an image does, without asking for one: an `<img crossorigin>`, or a CSS mask or shape from `/media/`, doesn’t load.
- **No popups; links through the bridge** ([#1480](https://github.com/HJeon139/postbox/issues/1480)): the policy never gets `allow-popups`. In the Claude desktop app’s browser pane, an app’s `window.open` with no click replaced Postbox’s own page, from a hidden check frame and on opening a conversation, and Postbox’s own `window.open` after a click did too (measured in the flexible-apps prototype, [#1475](https://github.com/HJeon139/postbox/pull/1475), on 17 November 2026). A link goes to Postbox over the bridge instead, which opens it only right after the person’s click or key press in that app, one link per click, and none where the message carries no snapshot of the click (Firefox and Safari): a new tab in a browser, the default browser from the pane (`app/js/app-links.mjs`). A click’s activation lasts about 5 s and nothing in the frame uses it up, so without the one-per-click rule a single click let an app open a burst of links and more on timers. A link to a place on the app’s own page, or relative to it, stays in the frame.
- **One turn per click, from the browser’s snapshot alone** ([#1488](https://github.com/HJeon139/postbox/issues/1488)): an app’s `postbox.send` starts its agent’s turn only when the message carries the click’s snapshot (`MessageEvent.userActivation`), and that event spends the app frame’s activation for about 5 s, so the frame’s later sends in them are notes (`app/js/app-send.mjs`). Nothing the app writes in its message counts, since its own code can post anything with the real activation attached. The cost is the same as for links: a second click in the same app within those 5 s is a note, not a turn.
- **Network through Postbox** ([#1482](https://github.com/HJeon139/postbox/issues/1482)): the frame loads nothing itself, and an app gets public data with `net.fetch`, which Postbox’s server runs (security-boundaries.md, “What leaves through net.fetch”). Planned ([#1610](https://github.com/HJeon139/postbox/issues/1610), decided in [#1604](https://github.com/HJeon139/postbox/issues/1604)): the server also fetches the person’s own network and reads files on disk with `fs.read`, under a grant the app’s agent sets (security-boundaries.md, “What leaves through net.fetch” and “What an app reads from disk”). Keeping the frame itself off the network costs an app no function: the pane blocks a sandboxed frame’s own requests anyway (“What it rests on”).
- **Forms submit to the app alone** ([#1476](https://github.com/HJeon139/postbox/issues/1476)): `allow-forms` lets a form’s submit event fire, which a sandboxed page without it never does, so Enter in an app’s form did nothing. `form-action 'none'` keeps the submission from going anywhere.
- **Framed by Postbox alone** ([#992](https://github.com/HJeon139/postbox/issues/992)): its policy ends in `frame-ancestors` naming the origin the request came to, `http://127.0.0.1:<port>` or `http://localhost:<port>`, from the `Host` header the request gate has already checked. Postbox’s page frames these pages only by relative URLs, so the page and its frames share that origin wherever it runs: a browser, the Claude desktop app’s browser pane, view_app’s capture. The two spellings are different origins, so the policy names only the one asked for, not both. It names the origin rather than `'self'`, because the page’s own origin is opaque.

**What it rests on**
- **Measured in the browser people use.** The Claude desktop app’s browser pane refuses to load any frame that has the `sandbox` attribute (`ERR_BLOCKED_BY_CLIENT`). It also blocks every request a sandboxed, opaque-origin page makes, while letting its inline scripts run. Headless Chrome allowed all of it, which is why the end-to-end runs passed while apps and diagrams stayed blank in the pane.
- **The same isolation.** The header sandbox gives the page an opaque origin, exactly as the attribute does. The host’s bridge only answers frames whose origin is `null`: if a page ever arrived without the header, it would be same-origin, and the bridge would shut it instead of serving it. A test checks that every sandbox page carries the policy.
- **Sturdier everywhere.** A page that needs no requests can’t be broken by an extension, a proxy or a slow network.

- **The network stays out of the frame, measured on 17 November 2026** (the flexible-apps prototype, [#1475](https://github.com/HJeon139/postbox/pull/1475), in Google Chrome 156 and the Claude desktop app’s pane, Chrome 156, against a local stand-in for a signed-in site and a server on the local network):
  - **A, the same sandbox with `connect-src *`:** the pane blocked every request from the frame. Chrome sent the stand-in’s `SameSite=None` cookie with a GET, a POST and an image (not its `Lax` or `Strict` ones), couldn’t read the responses, read and wrote to the local network server, and ran another site’s script. Postbox’s API refused it.
  - **B, no sandbox, same-origin:** in both browsers the app read `/api/state`, wrote to Postbox’s API as the person, and put a banner on Postbox’s page.
  - **C, `net.fetch` through Postbox:** it worked in both browsers, sent no cookies, and refused Postbox itself and the local network.

  C is the one that works where the owner runs Postbox, and the only one that carries none of the person’s browser sessions and can’t reach Postbox’s own API. Its refusal of the local network gave up function: an app can’t show a Ray job on the person’s cluster without its agent relaying the data. On 21 November 2026 the owner decided function first (#1604): the planned grant opens the person’s own network to an app whose agent could reach it, and keeps cloud metadata and other Postbox servers out. The code still refuses the local network until #1610 lands.

**Revisit when** apps need large assets of their own. Then serve them from a separate origin rather than relaxing the policy.
