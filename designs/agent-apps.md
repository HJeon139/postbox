# Agent apps and the block catalog

What agents send to Postbox: blocks from a fixed catalog, the events the page applies, apps agents write that run sandboxed in the conversation, and narration. The decisions behind them are in [architecture.md](architecture.md) and its children, chiefly [sandbox.md](architecture/sandbox.md) and [narration.md](architecture/narration.md).

## The block catalog

A block is JSON naming one component. Agents send it with the `show_block` tool. Every block has these fields:

| Field | Required | Notes |
|---|---|---|
| `id` | Yes | Letters, digits and `- _ . :`. Sending the same id with `update_block` replaces the block; one that asks again (a choice, form, confirm or review) moves to the newest point, with a line where it was. An id names one block of its agent’s in a conversation, so `show_block` refuses an id that agent already showed there. |
| `type` | Yes | One of the components below. |
| `version` | Yes | The component version. This app reads version 1 of each. |
| `title` | No | Up to 200 characters. |
| `fallback` | Yes | Plain text shown if the block can’t be rendered. Write it so the person can still answer in the chat. |

Every block is validated before it’s shown ([`shared/catalog.mjs`](../shared/catalog.mjs)). Objects are strict, so an unknown field is an error. `show_block` and `update_block` advertise each type’s JSON Schema, made from the catalog’s own rules ([`shared/block-json-schema.mjs`](../shared/block-json-schema.mjs)), so the model reads the exact shape; the few checks across fields that a schema can’t say, such as a select needing options, stay the catalog’s.

An agent’s invalid block is refused, and nothing is shown: the reply names each problem and shows a valid block of that type ([`shared/block-examples.mjs`](../shared/block-examples.mjs)), so the agent can fix it and send it again with the same id. A host refuses one the same way, before Postbox sees it. It was shown before, as its fallback text, and agents retried at once, mostly under a new id, so every try left a broken card in the conversation: 26 refusals in the UAT runs from 26 October to 13 November 2026, none followed by a read, 18 retried under a new id (#1319). An app takes Postbox’s type: one that applies a font of its own, by `@font-face`, `font-family` or the `font` shorthand in its CSS or style attributes, SVG’s `font-family` attribute, or a script that sets a font, is refused the same way ([`shared/app-fonts.mjs`](../shared/app-fonts.mjs), #1322). It may name the families in `workbench.css`’s text and mono stacks, which the sandbox inlines, and any generic family (`serif`, `monospace`…), so apps read as part of the conversation and draw in one family on every browser (#44). The usual platform fallbacks (Roboto, Helvetica, Arial and the like) may follow an allowed family, and emoji fonts may come anywhere. Only what an app applies is read: CSS it shows in `<pre>` or `<code>`, in a comment or in a script’s string is never refused. The scan reads the code once, with no pattern that can backtrack ([`shared/app-code-scan.mjs`](../shared/app-code-scan.mjs)), since it runs on the server on up to 600,000 characters. The refusal and `show_app`’s description name both stacks.

Only a block this Postbox can’t read but a newer host’s catalog took, of an unknown type or a newer version, still shows its fallback text and a collapsed **Show the raw block**, so it never fails silently and never breaks the transcript.

| Component | Fields | Your action → the event’s `action` and `values` |
|---|---|---|
| `choice` | `options: [{ id, label }]` (1–24), `prompt?`, `multiple?`, `max?`, `other?: { label, placeholder? }`, `submitLabel?` | `choose` → `{ selected: [ids], other? }` |
| `form` | `fields: [{ id, label, kind: text \| longtext \| number \| select \| toggle \| date, required?, placeholder?, help?, min?, max?, step?, maxLength?, options?: [{ id, label, description? }], default? }]` (up to 24, each label up to 120 characters; options for a select only, up to 50, as objects, never strings), `prompt?`, `submitLabel?` | `submit` → `{ [fieldId]: value }`, already checked: numbers are numbers, dates are `YYYY-MM-DD`, selects are option ids |
| `table` | `columns: [{ id, label, kind?: text \| number, sortable? }]`, `rows: [{ id, cells: { [columnId]: value } }]` (up to 5,000), `rowAction?: { id, label }` | `<rowAction.id>` → `{ rowId }` |
| `progress` | `steps: [{ id, label, state: pending \| running \| done \| failed, detail?, duration? }]` | None. Move it on with `update_block`. |
| `card` | `body?`, `facts?: [{ label, value }]`, `actions?: [{ id, label }]` (up to 3) | `<action.id>` → `{}` |
| `confirm` | `statement` (say exactly what will happen), `confirmLabel`, `cancelLabel?` | `confirm` or `cancel` → `{}` |
| `image` | `src` (https from an allowed origin), `alt` (required), `caption?`, `width?`, `height?` | None |
| `code` | `code`, `language?`, `filename?` | None. A Copy button is built in. |
| `review` | `format: markdown \| code \| app`, `content` (markdown and code), `appId` (app), `previous?` (shows a diff; Postbox counts revisions), `threads?: [{ id, line? \| anchor?, status: open \| resolved, comments: [{ author, text, edited? }] }]` (a new review’s comments are its agent’s, as its @handle; an update may echo the person’s comments under the name it read them by, and keeps only what the person wrote, #1208; `edited` marks the person’s correction of their last comment in the thread, added at its end, after any reply, #858), `language?`, `filename?`, `files?: [{ name?, path }]` (markdown: images from the agent’s folder, `path` where each is and `name` a plain file name, PNG, JPEG, GIF or WebP, that the content shows by name or path) | `submit` → `{ verdict: comment \| approve \| request_changes, comments: [{ line? \| anchor?, text }] }`; then `correct` → `{ threadId, line? \| anchor?, replaces, text }` when the person corrects a comment they submitted (#858): each correction is an event, so a turn, and the comment as sent stays in the thread, with the correction after it |
| `app` | `code` (HTML with inline script and style), `permissions?: [tool names]` | Whatever the app sends (see below) |

Long text fields (`prompt`, `body`, `statement`, review content) are Markdown. Short labels are plain text.

**Answering.** A `choice`, `form`, `confirm` or `review` turns read-only once you answer, and shows what you chose. Only a new block, or an update to the same id, can ask again. An update that sets `outcome` (Markdown, up to 500 characters) on an answered `choice`, `form` or `confirm` doesn’t ask: it reports the result as a line under your answer, the block stays answered, and its agent doesn’t need you. Your action also appears in the transcript as a short line in your voice, such as “Chose: weekly · Monday 9:00”. Your answer is for the revision you saw: if the agent changed the block while you were answering, Postbox refuses the answer, keeps what you entered, and shows what changed, so you answer again. And an update over an answer the agent hasn’t read yet (it waits while the agent works), whether it asks again or sets `outcome`, is refused, so your answer stays and no result lands under it unread. The refusal gives the agent your answer in full, and takes it from where it waited, so the agent reads it once, can update in the same turn, and isn’t given it again at its next one (#1810). Three still wait for the turn’s end: an answer over 16,000 characters, which the refusal can’t give whole; a correction of one of your comments, which the refusal doesn’t carry; and a `confirm`’s answer, which starts its own turn, since a turn that began with you confirming runs the command the confirm shows without asking you again. An agent working on a host still gets your answer when its turn ends, whole: its `update_block` is queued there, so it never reads the refusal in the call. An update that asks again after the agent read your answer keeps a receipt of it on a review: what you answered, for which revision and when, and that the agent has revised it since (#518). An open asking block makes its agent **need you**: its ring pulses and you get a notification. One shown while its agent’s turn runs on, asked again by an update in that turn, or a question shown when a host ends its AskUserQuestion call before reaching it (#1868), counts at once, in the top bar, the tab title and ⌃J; the pulse and the notification come when the turn ends, as the agent is still working until then. If you stop that turn, the block waits quietly, as an older one does (#1748), and so does a tool request or view request the turn raised (#1868). It stays quiet when you answer another of the agent’s cards, after a restart, and through another agent’s wake: the session records the turn you stopped, and its cards no longer count until you answer them or a later turn asks again (#1928). Only Stop and Send now do this: when a run clock’s pause or budget, or a hung host turn, stops the turn, the form keeps counting, so it never goes quiet and then rings again on an unrelated click.

**Safety.** Markdown is rendered by [`shared/markdown.mjs`](../shared/markdown.mjs), which escapes everything. Raw HTML is shown as text, links are checked and open in a new tab with `rel="noopener noreferrer"`, and nothing an agent sends becomes a tag, an attribute name or a style.

## The event shape

When you act in a block or an app, the agent receives one message:

```json
{ "kind": "event", "event": { "blockId": "start-book", "revision": 1, "action": "choose", "values": { "selected": ["walden"] } } }
```

The event is built and checked by [`shared/events.mjs`](../shared/events.mjs) before it’s sent. `revision` is the revision of the block you answered: 1 when it’s shown, and one more with each `update_block`. Apps’ events have none. A form with mistakes doesn’t produce an event: you see a message under each field instead (“Enter a number from 5 to 200.”). These are all the messages an agent can receive:

| `kind` | When | Fields |
|---|---|---|
| `user` | You wrote to the agent | `text`, `attachments` |
| `event` | You acted in a block or an app | `event: { blockId, revision, action, values }` |
| `agent` | Another agent woke it | `from: "@handle"`, `text` |
| `wake` | A wake-up it scheduled | `note` |
| `app-check` | An app it wrote failed the pre-display check | `appId`, `problems: [{ code, message }]` |
| `lint` | Its reply used terms it never defined | `undefinedTerms: [{ term, key }]` |
| `notice` | Something Postbox wants it to know, such as a wake you didn’t allow | `text` |

## Agent-written apps

`show_app({ id, title, code, permissions })` shows an app inline at the thread’s full width. The app runs in an iframe whose page is served with the policy `sandbox allow-scripts allow-forms`, so it gets an opaque origin and no same-origin access. (`allow-forms` only lets a form’s submit event fire, for the app’s script; `form-action 'none'` still stops the submission going anywhere, #1476.) (The policy is a response header rather than the iframe’s `sandbox` attribute, because some embedded browsers refuse frames with the attribute. Postbox’s bridge only answers frames with an opaque origin.) Its content-security policy allows its own inline code, the kit and bundled libraries, and nothing else: no fetch, no websockets, no form submissions, no nested frames. Data comes through Postbox instead: public URLs with `net.fetch`, and, planned (#1610), the sources its agent names, on the person’s own network and on disk, so an app shows live data without its agent relaying it. The page is served by [`server/sandbox.mjs`](../server/sandbox.mjs).

Inside the sandbox, the kit ([`app/kit/kit.js`](../app/kit/kit.js)) provides:

| Call | What it does |
|---|---|
| `postbox.ready` | Resolves to `{ state, theme, appId }` once Postbox says hello |
| `postbox.query(tool, args)` | Asks the host for data. It works only for tools in the app’s `permissions` that its agent also holds, such as `narrate.speak`. Every agent holds its conversation’s assets, so `assets.search` (the room’s text assets by words and meaning, a passage at a time) and `assets.list` need only the app’s `permissions`, as does `net.fetch`: `{ url }` → `{ status, type, text }` of a URL, fetched by Postbox’s server, which its agent’s activity shows (security-boundaries.md, “What leaves through net.fetch”). It fetches only public addresses. Planned (#1610): the sources the agent names when it shows the app, such as a Ray dashboard on the person’s cluster, and `fs.read` of a file or folder it names, such as the job’s log folder, live (“What an app reads from disk”). |
| `postbox.file(name)` | A data file the agent attached to this version with `files`, as text (#54). |
| `postbox.send(action, values, summary)` | The first send after your click or key press in the app sends one event to the agent, which starts its turn, with a line in your voice; `summary` shows beside it as the app’s own words. One click starts one turn, with nothing for you to allow, at most one per app every 5 s or so. Any other send (on load, on a timer, a click’s later sends, a second click within those 5 s, from an app that took the keyboard, and every send in Safari and Firefox) resolves `{ ok, noted: true }`: a note the agent reads with `read_app` at its next turn, with no turn, no card and no line in your voice ([#1488](https://github.com/HJeon139/postbox/issues/1488)). |
| `postbox.saveState(obj)`, `postbox.restoreState()` | Saved state survives unloading, reloading and new versions |
| `postbox.publish(data)` | Shares the app’s current data with its agent, up to 256 KB of JSON: no turn, no card, no line in your voice. Postbox sends the latest at most every 400 ms, in order. The agent hears at its next turn that the app published, one notice for a burst, and reads it with `read_app` (`server/app-publish.mjs`, [#1478](https://github.com/HJeon139/postbox/issues/1478)). |
| `postbox.anchors({ name: element })` | Parts you can pin review comments to. An app review also takes a comment on the whole app, with anchor “the whole app”, a name no part can take, and says when an app names no parts (#855). Commenting changes only what’s around the app: its frame stays, with whatever the person did in it (#1726) |
| `postbox.on('theme', fn)` | Light and dark tokens update by themselves; redraw canvas or D3 output here |
| `postbox.load('d3' \| 'katex' \| 'mermaid')` | Loads a bundled library |
| `postbox.charts.line / scatter / stacked / heatmap / table` | Charts built to the design rules, each with a Chart and Table view |
| `postbox.narration(el, passages, opts)` | A player that reads passages aloud with a local voice, with a transcript that follows along. Needs `narrate.speak`. |
| `postbox.narrate(text, opts)` | One clip, as `{ url, ms }` |

The stylesheet is preloaded, so apps use the same classes and tokens as Postbox, on the cool app stage.

**Links.** A web link in an app opens in a new tab when you click it, and never on the app’s own ([#1480](https://github.com/HJeon139/postbox/issues/1480)). The kit hands it to Postbox over the bridge, which checks the click as it does a send and opens one link per click (`app/kit/links.js`, `app/js/app-links.mjs`). A link to a place on the app’s own page, like `#end`, stays in the app. In the Claude desktop app’s browser pane, where opening a window replaces Postbox’s own page, Postbox’s server opens it in your default browser (`server/app-links.mjs`).

**What the agent reads.** `read_app { appId, from? }` gives an agent what an app in its conversation published, the notes the app sent its own agent without a click, and its saved state, in parts as `read_asset` gives an asset, framed as the app’s data rather than your words. Reading is how an agent sees what you did in an app without asking you or giving you a button to send it. A note holds up to 16 KB of JSON, and the browser sends an app’s latest note at most every 400 ms, with how many earlier ones it replaced. An app keeps 50 unread notes; past that, Postbox counts the ones it drops and logs nothing of them. Reading to the end takes the notes the read showed, and the agent hears of new ones at its next turn, one notice for a burst (`server/app-notes.mjs`). What an app published, and its notes, are kept in private records, not on the app, so neither sends a page anything ([security-boundaries.md](architecture/security-boundaries.md), “What reaches the browser”).

**Why a click is one turn.** The browser can tell a send came right after your click or key press in that app, and nothing else: it can’t tell one click’s first send from its seventh. An app’s button that sends seven events in one click used to send five and then raise a card asking you to allow the rest, and every later send, even a fresh click, waited behind that card; a send with no click was refused, so the agent never heard it ([#1488](https://github.com/HJeon139/postbox/issues/1488)). Now the first send of a click is its turn, and the click’s later sends are notes (`app/js/app-send.mjs`). The click’s activation lasts about 5 s and a send doesn’t use it up, so one event spends the app frame’s activation for those 5 s, as one link does (#1481), and the frame’s later sends in them are notes. Only the browser’s snapshot of the activation counts: anything the app writes in its message, it could forge (an app that tagged its own sends with made-up clicks got 12 turns from one click, in #1491’s review). **The cost:** one turn per click per about 5 s in each app. A second click in the same app within those 5 s is a note, not a turn. Past 30 events in a minute, an app’s next ones are notes too: never a card or an error. A browser without `MessageEvent.userActivation` (Firefox, Safari) can’t tell a click at all, so every send there is a note, and agents are told so.

**Images.** An app loads images from `data:` URLs, or from `/media/<name>`. That serves the media bundled with Postbox, then the `media/` folder in your data folder (`~/.postbox/media/`), where agents copy the images their apps show (PNG, JPEG, GIF, WebP, AVIF or SVG). Agents find it in `$POSTBOX_MEDIA`. Nothing an agent adds goes into Postbox’s own folder, which an upgrade replaces.

**The pre-display check.** Before you see an app, your browser loads it in two hidden frames, at 375 and 1280 px. It checks for:
- sideways overflow
- fields and buttons without labels
- images without alt text
- positive `tabindex`
- low-contrast text
- text cut off by its box. An ellipsis, a line clamp, or a gradient fade on the box that cuts it counts as cut short on purpose, so an app can fade its own text out where it ends without a finding; a fade on any other box, or a mask that isn’t a gradient, doesn’t ([#681](https://github.com/HJeon139/postbox/issues/681), `app/kit/check-text.js`)
- script errors
- in the 1000 × 680 frame, labels drawn over a chart’s dots, rings and lines, as a hint only the agent is told, for up to three charts: alone, it leaves the version passed, with no note for the person, since half of what it flags in real apps is a touch that stays legible. Alone, the agent hears it in the reply that waits for the check, or else in its turn’s lint, and `read_message` names it; beside a finding that holds the version back, it goes back with that finding, and it can never push one out. It tests the band of each label’s letters, so a mark that only grazes the space above or below them passes. A name inside its own dot or ring passes too, and so does one centered in its node, a closed outline up to 160 px (`app/kit/check-marks.js`, [#952](https://github.com/HJeon139/postbox/issues/952))

The first failure goes back to the agent as an `app-check` message. While a Postbox page in view can run the check (one that showed a conversation in the last 20 s; a background tab runs none), `show_app` and `update_app` wait for it, up to 12 s, and their reply says how it went, the problems it found included, so the agent doesn’t tell you a version is fixed before its check answers; a result the reply carries while the turn is running isn’t sent again as a message, and problems that arrive after the wait gave up (or after the turn was stopped) come as one (#337, `server/app-check-wait.mjs`). A version a newer one replaced, or whose app was retired, settles its wait at once, and a fix the reply carried ends with the turn that heard it, as an `app-check` turn’s does. With no page in view, the reply returns at once. An agent on a remote host still hears the check as a message. If the next version still fails, the app is shown with a note. A script error shows a “stopped working” card with Reload and Ask to fix.

What the check finds is written for the agent, with pixel sizes and CSS advice, so only the agent gets it: as the `app-check` message, or in a lint turn for warnings and for what a fix left. You see a plain status instead (#948, #981). While the agent fixes a version, you see the last version that passed its check, read-only, with a note; if none has, its place says the app is being fixed. An app shown with problems has one plain sentence above it: whether parts may be hard to read or use, whether its agent couldn’t fix them, or that Postbox couldn’t finish checking it, and that the agent has the details only when it was told.

**Lifecycle.** An app reloads from its saved state as you approach it, and unloads when it’s well off screen. A same-size placeholder keeps the transcript from jumping. An app that keeps drawing frames for 30 seconds with no input from you is reported to its agent at its next turn, once per version, with how to make its loop stop on its own if nothing needs to keep moving; you see nothing, since only the agent can fix its app (`app/kit/frames.js`, `server/app-animating.mjs`, [#438](https://github.com/HJeon139/postbox/issues/438)). The agent guide says it first, so an agent writes the loop that way from the start: “Stop loops when nothing moves; cap their history” ([#1684](https://github.com/HJeon139/postbox/issues/1684)). A new version brings the app to the newest point in the conversation, beside the agent’s note about it, and leaves one line where it was that leads to it. It’s the same app, with its saved state, and older versions stay in its version menu.

## Narration

Agent apps can read text aloud with `postbox.narration(el, passages)`, a player whose transcript follows the voice, or `postbox.narrate(text)` for one clip. The app needs the `narrate.speak` permission, and its agent the tool.

The voice is [Kokoro](https://github.com/hexgrad/kokoro) (via `kokoro-js`). It runs on this computer in a child process, so its native packages stay out of the server. The model, about 100 MB, downloads into `models/` in the data folder the first time anything is read aloud. After that, a passage takes a second or two, and the same text is never synthesized twice. See the narrated walkthrough in [designs/recipes.md](recipes.md).
