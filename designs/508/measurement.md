# #508 measurement: PF-1 and the server, before and after #712b

#508’s action 1 asked for PF-1 and the snapshot stall from #578, measured before and after #712. #712 was split in two:
- #712b (#769) indexes items by id in `shared/state.mjs`, so reads and writes by id no longer scan a list;
- #712a, which skips drawing items far off screen, moved to sprint 4.

So this note has the before numbers and the after numbers for #712b alone. **PF-1 is not met this sprint.**

researcher read the first before numbers; critic reads this note.

## How it was measured

- **The machine:** the shared build host. It runs Linux 6.12 on x86_64, with an Intel Xeon Platinum 8375C and 32 cores. The runs used Node 24.21.0 and headless Chromium through `tools/browser.mjs`, which doesn’t use Playwright, so Playwright’s trace snapshots play no part.
- **The rooms:** generated by the big-room seed (`tools/uat/big-room.mjs`), with 1,000, 4,000 and 10,000 items. The 1,000-item room is 1×.
- **Commands,** from the repository’s root:
  - `node tools/bench-key-frame.mjs --sizes 1000,4000,10000 --keys 200 --runs 3`
  - `node tools/bench-server.mjs --sizes 1000,4000,10000 --runs 3`
  - `node tools/bench-snapshot-stall.mjs --snapshot <copy> --iterations 10`
- **Fairness:** the before and after runs of each pass ran one after the other, in one session, holding the gate lock. Each number below gives its pass, commit and load average. The gate lock holds back gates only, not other agents’ browser or UAT runs, so the load average is the best record of how busy the host was.
- **The real snapshot:** a 2.53 MB copy of one real host’s store snapshot, with top-level keys `turn`, `home` and `threads`. It isn’t filtered. The copy stays on the host, and only its size and the timings are reported.

## PF-1: a key press to the next frame

PF-1 (`requirements.md:82`) asks for a large room’s key-to-frame p95 within 10% of the 1× room’s. This sprint it’s measured in Chromium only, on generated rooms. Safari’s idle painting isn’t measured. `requirements.md:82` and `:207` still say “copies of real rooms” until the tool’s PR rewords them.

Each size had 200 keys × 3 runs, 600 keys in all. In every run below, every key had an Event Timing entry, so no p95 is a filled-in default.

| Pass | Commit | Load average at start | 1× p95 | 4× p95 (ratio) | 10× p95 (ratio) | PF-1 |
|---|---|---|---|---|---|---|
| First before run, 17:55 UTC | `ee5fa4d5` | 3.95 | 40.0 ms | 136.0 ms (3.40) | 336.0 ms (8.40) | fail |
| Before, 22:11 UTC | `99c15ffa` | 6.70 | 32.0 ms | 144.0 ms (4.50) | 336.0 ms (10.50) | fail |
| After #712b, 22:17 UTC | `6fd9c743` | 2.52 | 32.0 ms | 144.0 ms (4.50) | 344.0 ms (10.75) | fail |

The p95 figures are Event Timing’s. The tool’s own next-frame timer agrees with Event Timing within 4% at every size: 343.1 ms before and 340.7 ms after at 10×.

**#712b doesn’t change PF-1, as expected.** The time to the next frame in a long room goes on the page’s style and layout over every item it draws, which is #712a’s part. Event Timing reports in 8 ms steps, so 336 ms against 344 ms at 10× is one step, within the noise. The 1× p95 moved between 40 ms and 32 ms with the host’s load, so each ratio has to be read against the 1× figure from the same pass.

## The server

### The snapshot stall (#578; the budget is 50 ms)

The server passes ran at 22:23 UTC, before then after, at load averages of 1.36 and 1.01.

| Items | Before: stall max (`99c15ffa`) | After: stall max (`6fd9c743`) | Earlier before (`ee5fa4d5`) |
|---|---|---|---|
| 1,000 | 2.2 ms | 2.2 ms | 3.2 ms |
| 4,000 | 5.0 ms | 4.9 ms | 5.6 ms |
| 10,000 | 10.4 ms | 10.6 ms | 12.1 ms |
| The real copy, 2.53 MB | 26.03 ms | 26.72 ms | 26.64 ms |

Every stall is within budget, before and after, so S2 (splitting the snapshot) stays on hold (`storage-design.md:261`). The index lives outside the state, so the snapshot doesn’t change size.

### Reads and writes by id

| Measure, p95 | Size | Before (`99c15ffa`) | After (`6fd9c743`) |
|---|---|---|---|
| A streamed `item.text` chunk | 1× | 13.5 µs | 1.5 µs |
| | 4× | 36.8 µs | 0.3 µs |
| | 10× | 152.8 µs | 0.3 µs |
| Startup, replaying 5,000 log events | 1× | 82.1 ms | 12.7 ms |
| | 4× | 224.6 ms | 13.0 ms |
| | 10× | 662.5 ms | 18.7 ms |
| `/api/state` (2.0 MB at 10×) | 1× | 3.8 ms | 3.0 ms |
| | 10× | 17.5 ms | 17.7 ms |

**What #712b changed on the server:**
- **A streamed chunk:** each chunk finds its item through the index in constant time, where before it scanned the conversation’s list. At 10×, the p95 falls from 152.8 µs to 0.3 µs. The worst chunk was 1.72 ms at 10×. That’s probably the first chunk in a list, which builds that list’s index, but this run doesn’t show it.
- **Startup:** replaying the log no longer scans a list once per event. At 10×, it falls from 662.5 ms to 18.7 ms.
- **`/api/state`:** unchanged, since it still serializes the whole state.
